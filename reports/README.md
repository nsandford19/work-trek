# Reports

## The rule

**A report is never canonical state.** It is a snapshot of what GitHub Issues said at a moment
in time. If a report and the issues disagree, the issues are right and the report is old.

Agents must never answer an operational question ("what is blocked?") from a report. Always
query live — see [`../agent/CONTEXT_MAP.md`](../agent/CONTEXT_MAP.md).

## Generated output is not committed

`reports/generated/` is **gitignored**. Anything computed on demand — status summaries, the
output of `mc next`, ad-hoc queries — belongs there, or nowhere.

Committing generated status was considered and rejected: it goes stale the moment an issue
changes, it conflicts when two machines regenerate it, and it fills `git log` with noise that
destroys its value as a historical record. This is also why there is **no `CURRENT.md`**;
current state is computed on demand instead. Reasoning:
[`../ARCHITECTURE.md`](../ARCHITECTURE.md) §2.4.

## What *is* committed

`reports/weekly/YYYY-MM-DD.md` — deliberate, human-authored weekly reviews.

These are committed because they are a genuinely different artefact from a status dump: written
once a week, containing judgement rather than a query result, and valuable *because* they are a
frozen historical record. They answer "what was I thinking in August?" in a way live state
never can.

`reports/history/` — work-history ledgers and narratives, answering "what have I done this
year?". Ledgers are generated by `mc history sync <owner/repo>` but committed anyway: closed
PRs and issues are frozen facts, so regeneration converges instead of going stale or
conflicting — the same rationale as weekly reviews, unlike live-status output. Rules and
layout: [`history/README.md`](history/README.md).

A weekly review might cover: what was finished and what it cost, decisions made, what was
learned, what stalled and why, what should change next week. Use
[`../templates/weekly-review.md`](../templates/weekly-review.md).

```
docs(report): weekly review 2026-08-10
```

## On-demand reports

Ask for these in a session; they are computed, shown, and discarded:

| Report | How |
| --- | --- |
| What should I work on | [`../skills/whats-next`](../skills/whats-next/SKILL.md) |
| Active initiatives | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state open --label type:initiative` |
| Blocked work | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state open --label status:blocked` |
| Waiting, with staleness | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state open --label status:waiting --json number,title,updatedAt` |
| Recently completed | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state closed --limit 20 --json number,title,closedAt,stateReason` |
| Stale investigations | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state open --label type:investigation --json number,title,updatedAt` |
| Decisions this month | `git log --since="1 month ago" --diff-filter=A --name-only -- '**/decisions/**'` |
| New durable knowledge | `git log --since="1 month ago" --diff-filter=A --name-only -- knowledge/` |
| Repositories with active work | `gh issue list -R {{GITHUB_OWNER}}/{{CONTROL_PLANE_REPO}} --state open --json labels` → `project:*` → `repositories/*.yaml` |

A weekly review is just a human writing down the interesting parts of several of these.

## Deferred

Scheduled report generation (daily briefing, automatic weekly summary) is intentionally not
built. The trigger to build it: wanting the same report by hand most days for two weeks.
